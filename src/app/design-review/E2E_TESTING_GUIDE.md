# 🧪 End-to-End Manual Testing & QA Guide

This guide explains how to mock and verify the **Code-First AI-Reviewed Workflow** from start to finish. Use this to validate that the connections between the Agent Chat, GitHub, and the Design Review Dashboard are working correctly.

---

## 🎭 The "Hats" (Roles & Environments)

To test this E2E, you will need to switch between three roles. Each role has a specific "Home" where they perform their work.

| Role | Environment | Responsibility |
| :--- | :--- | :--- |
| **1. The Product Manager (PM)** | **Dashboard / Chat** | Defines features and kicks off the UI Spec. |
| **2. The Designer** | **Dashboard / Chat** | Defines visual specs via Figma and kicks off UI Spec generation. |
| **3. The Developer (Dev)** | **Local IDE / Chat** | Wires data/logic OR initiates a review from an existing PR. |
| **4. The Auditor (AI)** | **Background** | Performs automated gates and grades implementation. |

---

## 🛠 Preparation: Setting the Foundation

Before testing, ensure your project is configured in the **Settings > Project Integrations** panel:

1.  **Component Output Path**: Set to a relative path (e.g., `src/components`).
2.  **Discord Webhooks**: (Optional) Add webhook URLs if you want to see the automated pings.
3.  **API Keys**: Ensure a Figma PAT and Chromatic Token are configured (even if mock values for now).

---

## 🎬 Phase 1: Initiation (PM Hat)

**Environment:** *Agent Chat (Tech-Lead Stack)*

1.  **Action**: Open the Agent Chat and request a new component.
    - **Command**: `Run the ui-spec-generator workflow. I need a "ProjectCard" component.`
    - **Designer Variant**: `Run the ui-spec-generator workflow for this Figma design: [URL].`
2.  **AI Verification**: The AI should:
    - [ ] Create a new branch `feature/ui-spec-project-card`.
    - [ ] Implement the component in your specified `designSystemPath`.
    - [ ] Push the branch to GitHub.
    - [ ] (If configured) Send a Discord ping to the Dev team.

---

## 🎬 Phase 2: Implementation (Developer Hat)

**Environment:** *Your Local IDE*

1.  **Action**: Pull the new branch generated by the AI.
    - `git fetch origin && git checkout feature/ui-spec-project-card`
2.  **Logic Wiring**: In your IDE, use your local AI Agent to add a simple `onClick` handler or wire it to a mock data prop.
3.  **PR Creation**: Commit your changes and open a Pull Request on GitHub.
4.  **Developer Start (Alternative)**: If the feature wasn't started by a PM, you can trigger the review yourself:
    - **Command**: `Run the pr-design-review-init workflow for this PR: [GitHub URL].`
    - **Dashboard Action**: Or click **"New Review"** in the dashboard and paste the PR URL.

---

## 🎬 Phase 3: The Design Review (The "Gate" Hat)

**Environment:** *Design Review Dashboard*

**This is the most critical phase for testing the code we just built.**

1.  **Session Creation**: Once the PR is opened, a new session should appear in the **Design Review Queue**.
2.  **AI Audit**:
    - The AI Tech-Lead scans the PR.
    - It updates the **Gate Results** (Shadcn usage, Token alignment, etc.).
    - You will see the **Alignment Score** update on the dashboard.
3.  **Feedback Loop**:
    - If the score is `< 90%`, the AI will block the PR.
    - **Test this**: Intentionally use a non-brand color (like `bg-[#ff0000]`) in your IDE and push. Watch the dashboard update with a "Fail" gate.

---

## 🎬 Phase 4: Final Sign-off (Designer Hat)

**Environment:** *Design Review Dashboard*

1.  **Verification**: Once the AI Audit passes (Score ≥ 90%), the session status moves to `READY_FOR_DESIGNER_GATE`.
2.  **Human QA**: As the "Designer," click into the session.
    - [ ] Review the **Design Resource Panel** on the left to compare against Figma/Tailwind docs.
    - [ ] (Future) View the **Live Figma Embed** to see the source of truth.
3.  **Approval**: Click the **"Approve Visual Parity"** button.
4.  **Final State**: The session should move to `COMPLETED`, and the PR is now "Cleared for Merge."

## ❓ FAQ & Troubleshooting

### Why am I not seeing the session in the dashboard?
Ensure the `projectId` sent by the GitHub Action matches the `id` of the project in your database. Check the server logs for `[POST] /api/design-review/session` errors.

### Why is the Developer not using the Dashboard to code?
Because coding is best done in the IDE. The Dashboard is a **Governance Tool**. It ensures that no matter how many AI Agents or Developers are writing code, the **Visual Quality** and **Brand Parity** remain consistent.

### How do I "mock" a Chromatic build for testing?
In the `ReviewSessionMetadata`, you can manually patch a `chromaticBuildUrl` via the DB or API to see how the "Live Design Embed" links behave.
